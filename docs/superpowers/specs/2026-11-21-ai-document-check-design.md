# Slice 3: the advisory AI document check

Status: draft for Drew's approval, 2026-11-21. Items marked *(my call)* are the controller's proposals and are open to correction.

## Intent
This is the last v1 slice and the AI half of the case study.

After bids open, the office checks each bid's documents against the solicitation's requirements. Most real bids are scans with handwriting, so the checking is slow and error-prone. The check is a MET / NOT MET list per required section.

An AI reads each document and reports, for each checklist item, one of three results with evidence:
- **met**
- **not met**
- **unclear**

The evidence is the document, the page and an excerpt. The reviewer decides; the AI never does.

## Decided by Drew
These come from `docs/decisions.md` (2026-11-16) and from the 2026-11-21 conversation.
- **Advisory only.** The check never rejects a bid and never sets an outcome. The reviewer confirms or overrides each item, and an override needs a reason. Everything is logged.
- **Output.** Each item is met, not met or unclear, with evidence (document, page, excerpt). There are **no confidence scores**.
- **Who checks what:**
  - Structured fields are checked by rules, with no AI.
  - Documents are checked by the AI.
  - Where an item is a comparison (amount in words against the total, a name, a list of addenda), the AI only extracts the value, and a rule does the comparison.
  - The checklist shows which method produced each item.
- **The AI checks compliance, not award.** It gives no scores, rankings or recommendation.
- **Scans need vision.** Plain text extraction is not enough.
- **What is checked (option 1).** The office scans each bid's mailed signed original and attaches it. The AI checks that scan plus the bidder's uploads.
- **Provider.** OpenAI, with Drew's API key.
- **Safety rails:**
  - Only office staff can trigger a check, and only after close.
  - Usage caps, and a kill switch.
  - The key is read only on the server.
  - Seeded bids carry recorded results, so the public site shows the feature without live calls.
- **Evaluation.** Fictional bids with planted defects. A false "met" is reported separately from a false "not met", because passing a non-compliant bid is the costly error.
- **Approach A** (Drew: "your call", controller's pick). An office click runs the check in a server action, with one document per model call. Results are stored in Postgres.

## Carried constraints
- **Sealing.** No AI process sees bid contents before close. Document checks only run once `app.bids_closed`, and they read files through the same post-close office path as opening (`can_read_bid_file`, `opened_bid_files`).
- **2b review is unchanged.** Outcomes, grounds, the cure, flagged decisions, recap and award work exactly as today. The check feeds the reviewer's judgement and writes nothing to `bid_outcomes`.
- **Fictional data only.** Test documents are generated by us. Nothing comes from `source-docs/`.
- **Every guarantee is in Postgres with pgTAP.** Definer functions, the lock → check → write → audit pattern, and append-only logs.

## Goals, non-goals, anti-goals
**Goals:**
- the office can scan in each signed original after close;
- the office runs a check per bid, and the results show beside the bid on the review screen;
- the reviewer confirms or overrides each item;
- caps, a kill switch and recorded results for seeded bids;
- a repeatable evaluation run over a planted-defect set.

**Non-goals:**
- checking the performance bond or anything after award;
- an AI check of the solicitation itself;
- OCR or image pre-processing on our side;
- retries and background queues (approach B);
- any self-serve demo mode beyond the recorded seed results.

**Anti-goals:**
- the AI changing an outcome, a rank or an award;
- a confidence score;
- the API key reaching the browser or the repo;
- any check of a bid before close;
- a public or bidder action that costs API money.

## Approaches
- **A. Synchronous per document (chosen).**
  - "Run check" starts a run. The browser then calls one server action per document, so no single request handles the whole bid and any host's time limit only has to cover one document *(my call: the host isn't chosen yet)*. Each action sends its document to OpenAI, asks for structured output, and stores the result as it comes back.
  - A "running" row stops a double-click from paying twice.
  - Cost: a whole bid can take 30 to 90 seconds; one call per document keeps each request short. Hosted request time limits are the known risk.
- **B. Background queue.** A jobs table plus a worker (an Edge Function or a scheduled script). It handles long runs and retries better, but it's another deployed piece. If hosting limits bite, A's stored results move to a queue unchanged.
- **C. Recorded results only.** No live calls at all, so the feature doesn't really exist. Rejected.

## Design

### 1. Scanning the signed original
- After close, an office user attaches a PDF scan to a bid's logged signed-form original: "Attach scan" on the originals log.
  - It is stored in the sealed `bid-files` bucket under a new path, for example `bids/{bid_id}/originals/{log_entry_id}.pdf` *(builder's choice)*.
  - The office may read the file only after close.
- **Upload limits.** Before close, the upload is refused. One scan per log entry. Replacing a scan adds a new one; the old one is kept and marked superseded.
- **Paper bid bonds.** They are scanned the same way, against the bond's log entry.
- **No scan yet.** "Run check" still runs on the uploads, and the scan's items show as unclear with the note "Scan not attached" *(my call)*. Attaching a scan later and running again fills them in.
- **Size and pages.** A scan is a PDF of at most 20 MB and 30 pages *(my call)*.

### 2. The checklist
Items are fixed per document kind, with stable codes. The AI extracts or judges; rules compare.

| Document | Item | Method |
|---|---|---|
| Signed bid form scan | Signature present on the signature page | AI |
| | Amount in words matches the portal base total | AI extracts, rule compares |
| | Addenda listed match the published addenda | AI extracts, rule compares |
| | Form version (footer) matches the version submitted | AI extracts, rule compares |
| | Resident certificate number matches the claim (if claimed) | AI extracts, rule compares |
| Insurance certificate | Insured name matches the bidder's legal name | AI extracts, rule compares |
| | Coverage in force on the bid due date | AI extracts dates, rule compares |
| Bid bond (upload or scan; only when required) | Principal matches the bidder's legal name | AI extracts, rule compares |
| | Obligee is the agency | AI extracts, rule compares |
| | Surety signature present | AI |
| Qualifications, References, Current work (when required) | The document is what its slot says | AI |

- **Rules that compare values** live in TypeScript `src/domain/aicheck/`:
  - names are compared loosely (case, punctuation, "LLC"/"Inc.");
  - amounts are compared to the cent after parsing the words;
  - dates are compared in `settings.timezone`.
- **A missing extraction becomes "unclear"**, never "met".
- **Online acknowledgment wins.** Per 2c, the addenda on the form are compared, and a mismatch is a finding (not met) for the reviewer. The online acknowledgment stays authoritative for the 2c flag.

### 3. The model call
- **One call per document** to the OpenAI Responses API, with the PDF as file input and a strict JSON schema for the response.
  - The schema lists exactly that document's item codes.
  - For each code it returns: `result` (met | not_met | unclear), `page` (int or null), `excerpt` (≤ 300 characters), and `extracted` (string or null).
- **The prompt** says the document is untrusted bidder material. Instructions inside it are ignored, and the model reports only what it sees.
  - The structured schema and the advisory role are the real guard: a manipulated document can at worst mislead the reviewer, who sees the page and excerpt.
- **Model** from `OPENAI_MODEL`. The builder picks a current vision-capable default from OpenAI's docs at build time. Temperature as low as the model allows *(my call)*.
- **The key** comes from `OPENAI_API_KEY`, read only in the server module that makes the call. It is never `NEXT_PUBLIC_`, never committed, and never sent to the browser.
- **Timeouts and failures.** A call that times out or fails records a "failed" result for that document with the error class (no key, no document text), and that document's items show as unclear. The reviewer can run it again.

### 4. Storage and audit (Postgres)
- **`ai_check_runs`**: one per run of a bid. Columns: `bid_id`, `started_by`, `started_at`, `finished_at`, `status` (running | done | failed), `model`, and the solicitation and bid versions checked.
  - A partial unique index allows only one `running` row per bid.
- **`ai_check_items`**: append-only. Columns: run, document (slot or log entry plus storage path), item code, method (ai | rule), result, page, excerpt, extracted value, and comparison detail.
- **A run that stops mid-way.** A `running` row older than 10 minutes counts as failed, so a crashed action never locks a bid *(my call)*.
- **Re-running one failed document** adds items to the same run and counts against the daily document-call caps, not the per-bid run cap *(my call)*.
- **`ai_check_reviews`**: append-only. The reviewer's confirm or override per item, with the reason required for an override, the user and the time. The latest row wins. Reviews belong to an item, so a new run starts unreviewed. Earlier runs and their reviews stay in the history *(my call: a new run may read the document differently, so old confirmations shouldn't carry over)*.
- **Writers** are definer functions. The server action calls them as the office user. It never uses the service key. Only the raw model response is passed in, and the rule comparison runs in TypeScript before the write *(my call: TS owns parsing; SQL owns who, when, sealing and caps)*.
- **Integrity of writes** *(my call)*:
  - Office staff are trusted to store what the model returned. The guards are structural:
    - items can only be written to a `running` run that the caller started;
    - item codes must belong to the document kind;
    - `recorded = true` has no API path: only the seed sets it.
  - Moving the name, amount and date comparisons into SQL would duplicate parsing for little gain.
- **Reads** are office only, after close. The agency, bidders and the public never see check results, recorded ones included *(my call)*. Bid documents stay confidential after close; only the recap is public.

### 5. Caps and the kill switch
Caps are enforced in SQL when a run starts *(my call, values in `settings`, admin-editable)*:
- at most 3 runs per bid;
- at most 50 document calls per office user per day;
- at most 200 document calls a day in total.

Past a cap, "Run check" is disabled with the reason.

The kill switch is `AI_CHECK_ENABLED` (env). When it's off, the button is hidden, a note says checks are turned off, and recorded results still show.

Drew should also set a monthly spend limit and a project-scoped key in the OpenAI dashboard. That's a runbook line in the README, not code.

### 6. The review screen
- **Per bid**, a "Document check" panel on `/office/solicitations/[id]/review`, beside the existing row:
  - the run status and a "Run check" button, with the cap reason when it's disabled;
  - the items grouped by document, each with its result badge, method label (AI or rule), page and excerpt, and a link that opens the document at that page;
  - Confirm and Override (with a reason) per item.
- **A summary per bid:** counts of not met and unclear.
- **No colour-only status**, and `ConfirmAction` for running a check, since it costs money.
- **The bid's outcome controls are unchanged.** The panel informs the reviewer and has no buttons that set outcomes.

### 7. Recorded results and seeds
- **27-0003's four closed bids get:**
  - seeded scans: generated fictional PDFs (§8), stored as seed objects if the seed can place them; otherwise the results show "scan not available" *(builder checks feasibility)*;
  - one recorded run each, with item results that include planted findings:
    - Juniper: amount in words doesn't match the total;
    - Basalt: missing surety signature;
    - Granite: insurance expires before the due date.
- **Recorded runs** are flagged `recorded = true` and labelled "Recorded result" in the UI.
- **Who sees them on the hosted site** *(my call)*: anyone signed in as office staff, as in a screen-shared walkthrough. The decision on record is that the demo is a walkthrough, not self-serve, and results never become public because bid documents stay confidential. If you later give visitors an office login, leave `AI_CHECK_ENABLED=0` on the hosted site so they see recorded results and can't spend money.
- **Seed files.** SQL can't upload bytes, so a local script (`npm run seed:files` *(builder's name)*) uploads the generated fixture PDFs for the seeded bids to local storage after `db:reset`. Without it, the recorded results still show and "open at page" says the file is unavailable.

### 8. Test documents and evaluation
- **A script** (`scripts/aicheck-fixtures.mjs` *(builder's name)*) generates fictional documents with the existing playwright PDF renderer:
  - filled bid forms with signature and checkmarks as images, rasterized to image-only PDFs to imitate scans;
  - insurance certificates and bonds.
  - Each has a manifest of its planted defects.
- **An evaluation script** (`npm run aicheck:eval`) runs the checks against the set with the live API:
  - it is run by Drew manually; it is never in CI and never in `npm test`;
  - it prints per-item confusion, with the **false met** rate shown separately from **false not met**;
  - it writes a dated report under `docs/evaluation/`.
- **Unit tests use recorded model responses.** Vitest and pgTAP never call OpenAI.

- **Inputs the rules need** all exist already:
  - the base total, from `bid_versions` prices and the published snapshot;
  - the resident claim and certificate (0019);
  - the version submitted;
  - the published addenda (2c);
  - the required upload slots, from the snapshot and `app.required_bid_slots`.
